# 执行与记录

## 状态和记录方式

候选使用稳定 ID，状态至少区分：待审核、批准、保留、执行前已不存在、已清理、部分清理、暂缓。批准对应具体候选版本和范围；出现路径复用、未知内容、用途改变或备份安排改变时，记录差异，不能把旧授权移植到新内容。

执行记录至少包含：

| 字段 | 含义 |
|---|---|
| 时间与时区、批次/候选 ID | 连接时间线，区分同名项目的不同阶段 |
| 精确目标与身份 | 路径、快照名、应用/版本或有条件的文件选择规则 |
| 授权依据与保留边界 | 用户实际决定及其适用版本；历史文件里的许可不算新授权 |
| before | 存在状态、大小/单位/统计方法、身份、占用、执行前 df |
| 备份及验证 | 是否要求备份，副本位置、验证级别、源是否变化、当前是否可恢复 |
| action 与逐项结果 | 方法、退出码、异常、实际触及的子路径；日志不含密码或凭据 |
| after/verification | 具体目标与保留路径复查、失败和未知、执行后 df |
| 恢复与影响 | 重装、下载、重建条件，以及无法从该批恢复的内容 |

先写 plan/before，再逐项写 action/after，异常和 finally 分支也保存记录。不要把成功日志一直留在内存里，到整批最后才写盘。自动化失败、部分删除或备用方式改变了原方法，都应留下事实和证据缺口。

“目录存在”不是完整保留验证；SHA-256 清单也不是内容备份。用户要求保留一份再删时，核对文件集合、内容或适当的完整性条件，确保源在验证后未变，再清源。没有备份的项目写清重新取得内容的条件。备份删除后保留其历史验证，但当前状态更新为不可用。

## 几个容易误报完成的场景

- 工具 dry-run 没有真正执行；UI 点击只到了中间页面；退出码失败却有部分成功输出。成功必须由目标和保留边界复查支持。
- 目录删除中途失败：记录已清子项和残留，继续其他独立的已批准目标，不能称整目录消失。
- 缓存被应用重建：区分老缓存已清、新缓存生成与从未删除；别不停追删活跃缓存。
- 音频驱动文件删除后可能仍被进程加载，重启后的设备变化与当下删除结果需要分开记录；不要为了立即卸载强行重启音频服务。
- NAS/SMB 返回“目录非空”或“可列出但 unlink 找不到”：先查看实际残留、打开句柄和服务端行为。只对批准目录内明确的元数据项做有限诊断/重试，不改 NAS 全局设置，也不把部分成功写成完整删除。
- 数据卷空间可能暂时不增加：快照、后台写入和共享块可能保留空间；不凭这种现象重复删已经清过的资料。

## 维护档案

按用户指定位置建一个日期目录，用总览、逐项记录/证据、故障速查和校验清单组织；记录较少时合并文件即可。既有备份留在原位，只增加索引。没有指定位置时选择已授权的本地工作位置，并告知实际保存路径；不要擅自选择外部云服务。

总览要保留“清理开始前、各批执行时、备份后来被删除、最后复查”的时间关系。历史证据不覆盖；当前候选表移除已经处理的项目，暂缓和保留另列。对存放到 NAS 的记录读回核验，准确说明是否做了大小、文件集合或内容哈希验证。

归因速查按“症状 → 实际相关改动 → 先检查什么 → 恢复条件”组织，把关联线索与已确认故障分开。让下一位操作者先记录错误原文、版本、重现步骤和重启/更新时点，再做小范围补救；补救动作另开记录。

分享 skill 时只放通用规则、合成示例和必要工具。个人维护报告、硬件标识、书目、账号、NAS 地址、私有路径和历史删除脚本不默认发布。用户的保留清单只对其会话适用，不写成全体使用者的强制偏好。
